## 1. 唯一要件源

### 1.1 SPEC.md 由来（原文の範囲）
- **目的**: RTL-SDR で raw IQ を受信し、ISDB-T のワンセグでデコードして TS を HTTP stream で流す。
- **実装言語**: Rust。
- **コマンド名**: `ts-stream`。
- **サブコマンド**: `list-devices` / `server --host 0.0.0.0 --port 3000 --device 0`。
- **HTTP API**: `GET /stream?ch=19`（chunked transfer encoding）、`GET /version`。

  少なくとも N100 (Intel) と OrangePi PC2 で動かす。

## 2. 委任された設計判断（本計画で確定）

ユーザー回答を受け、以下は実装者が判断して確定した事項である。追加承認は要さない。
`/version` の扱いは §4 の確定方針に従う（排他に含めない）。

### 2.1 排他・ライフサイクル
- **ストリーム枠は 1**。追加 `GET /stream` は同一 ch・別 ch を問わず `409 Conflict`。
  `/version` はこの排他に含めない（§4）。
- **チューニング / ロック待ち段階から原子的に予約**し、競合させない。
- 予約解放は **cleanup / cancel / join の完了後のみ**行う（全箇所で統一）。
- `stopping` 中の追加 `GET /stream` は再 open せず `409` を返す（`/version` は通常応答）。
- 停止の契機は、唯一の client の離脱、初期ロック timeout、再取得 timeout、USB / DSP の fatal エラー、
  遅読による当該接続終了、SIGINT / SIGTERM であり、いずれも `stopping` を経由する。
- 多重配信・クライアント別 fanout は**採用しない**。USB→DSP と DSP→単一 HTTP の有界 queue に簡素化する。
- USB callback は**非 blocking にし、cancel / join を備える**。

### 2.2 CLI
- 既定 host `127.0.0.1`、既定 port `3000`、既定 device `0`。
- `--host` 指定は尊重する。SPEC の例 `0.0.0.0` はそのまま維持する。
- `list-devices` は stdout に `index` / `name` / `serial` を出力（serial 取得不可ならその旨を明示）。
  診断は stderr に出す。
- gain は既定 `auto`、任意で手動 dB 指定。ppm は既定 `0`。
- IQ replay はテスト内部用途とし、公開 CLI 機能にはしない。

### 2.3 HTTP / API
- HTTP/1.1。chunked framing は framework に任せる。`Content-Type: video/mp2t`。
- `/version` は JSON（`name` / `version`。`git` は取得可能な場合のみ含める）。
- ステータス: `400` 不正 ch / `409` 占有（追加 `GET /stream`）/ `503` device unavailable /
  `504` initial lock timeout。`/version` は全状態で `200` JSON（§4）。
- ヘッダ送信後の TS に JSON 等の非 TS データを混入させない。異常時はそのまま終了する。

### 2.4 規格・対応表
- UHF ch の許容範囲、規格 Mode / GI / 変調などの詳細は一次資料から対応表にする。
- **未測定・未実装の項目を「対応済み」と宣言しない**。

## 6. 構成 / データフロー

### 6.1 信号処理パイプライン（暫定）
部分受信として 13 セグメントの中央セグメントを対象に帯域抽出・リサンプルする。
```
RTL-SDR raw IQ
  -> 周波数補正 (ppm / DC offset)
  -> 帯域抽出（中央セグメント）
  -> リサンプル
  -> 同期（Mode / GI は同期で推定）
  -> FFT
  -> キャリア抽出 / 等化
  -> 周波数デインターリーブ
  -> 時間デインターリーブ
  -> シンボル軟判定
  -> ビットデインターリーブ
  -> デパンクチャ
  -> Viterbi
  -> バイトデインターリーブ
  -> エネルギー拡散除去
  -> RS(204,188)
  -> 188 byte TS パケット
  -> 単一 HTTP 有界 queue -> HTTP chunked 配信
```
- TMCC は制御情報の**分岐**として扱い、階層ごとの変調 / 符号化 / 時間インターリーブ長を取得する。
  Mode / GI は同期段で推定する。
- 上記の順序は**暫定案**であり、正確な規格順序・枝分岐は設計段階で一次資料・規格および
  検証用 fixture により確認して確定する。

### 6.2 スレッド / 非同期モデル
- HTTP（非同期, tokio）と、blocking な USB 読み出し・DSP を**分離**する。
- USB / DSP は専用スレッドで実行し、HTTP 層とは**単一の有界 queue** で接続する。
  クライアント別 fanout は持たない。
- USB 受信 callback は**最小コピー**を行い、有界 IQ queue へ**非 blocking で投入**する。
  DSP は別スレッドで queue から取り出して処理する。
- IQ queue が満杯の場合は当該バッファを drop し、drop を検出して**再同期**する
  （無言で隠さず、状態・集計カウンタに反映する）。
- 遅読（HTTP 側 queue 溢れ）時は当該接続を終了する。
- ログ可視化は stderr の診断ログと集計カウンタで行う（監視用 HTTP endpoint は追加しない）。
- 受信停止は librtlsdr 等を扱う**内部 API** として用意する。公開 endpoint にはしない。
  キャンセル・スレッド `join` を備え、**cleanup / cancel / join の完了後にのみ予約を解放**する。

## 7. サーバ状態機械と排他

- 状態: `idle` / `tuning` / `locking` / `streaming` / `reacquiring` / `stopping` / `error`。
- 1 サーバ = 1 デバイス = **ストリーム枠 1**。
- `idle` から `tuning` へ遷移する時点で**原子的に予約を取得**する。予約取得後の追加
  `GET /stream` は、同一 ch・別 ch を問わず `409`。
- `streaming` 中にロック喪失または IQ gap を検知したら `reacquiring` へ遷移する。
  - 再取得に成功したら `streaming` へ戻る。
  - 再取得は最大 **10 秒**（初期ロックの 10 秒とは**別枠**）。失敗したら `stopping` へ遷移する。
  - `reacquiring` 中も枠は保持し、追加 `GET /stream` は `409`。
  - ヘッダ送信後は非 TS のエラーを送らない。`reacquiring` 失敗時はそのまま接続を終了する。
- 停止の契機は、唯一の client の離脱、初期ロック timeout、再取得 timeout、USB / DSP の fatal エラー、
  遅読による当該接続終了、SIGINT / SIGTERM。いずれも `stopping` を経由する。
- 予約解放は **cleanup / cancel / join の完了後のみ**（§2.1 と統一）。それまで `stopping` 中の
  追加 `GET /stream` は再 open せず `409`。client が居ない `idle` の間だけ新規予約を受け付ける。
- `/version` は排他に含めない。`tuning` / `locking` / `streaming` / `reacquiring` / `stopping` /
  `error` の全状態で、HTTP サーバがリクエストを受け付けている間は通常どおり `200` JSON を返す。
  終了完了後の応答保証は不要。`/version` は受信枠を取得・消費せず、USB / DSP に依存させない（§4）。

## 8. HTTP / CLI 契約

- プロトコル: HTTP/1.1。chunked framing はフレームワーク（axum / hyper 等）に任せる。
- `/stream`:
  - `Content-Type: video/mp2t`、`Transfer-Encoding: chunked`（Content-Length なし）。
  - **chunk 境界と TS パケット境界は別物**。TS の 188 byte 境界を chunk 境界に合わせる必要はない。
  - ヘッダ送信後は HTTP status を変更できない。TS ストリームに JSON 等の非 TS データを
    混入させない。異常終了時はそのまま終了する。
  - ステータス: `400` 不正 ch / `409` 占有（追加 `GET /stream`）/ `503` device unavailable /
    `504` initial lock timeout。
- `/version`:
  - JSON（例: `{"name":"ts-stream","version":"x.y.z"}`）。`git` は取得可能な場合のみ含める。
  - `tuning` / `locking` / `streaming` / `reacquiring` / `stopping` / `error` を問わず、
    HTTP サーバがリクエストを受け付けている間は `200` JSON を返す。終了完了後の応答保証は不要。
  - 受信枠を取得・消費しない。USB / DSP の状態に依存させず、長い DSP 処理を待たずに応答する。
- セキュリティ:
  - 認証なしの公開は危険。既定は `127.0.0.1`。`--host` 指定は尊重する。

## 9. 段階別作業・成果物・完了条件・依存関係

各 Phase は原則前段に依存する。旧 Q 番号による着手ゲートは用いず、本計画の確定事項を前提に判定する。

### Phase 0: 一次資料・ライセンス・規格対応表
- **作業**: SPEC / 追加回答の整理、依存ライセンス確認、対象規格パラメータの一次資料確認、
  UHF ch 対応表（物理 ch・中心周波数・セグメント位置・許容範囲）の作成。
- **成果物**: 本計画、ライセンス確認メモ、規格対応表初版。
- **完了条件**: Phase 1 着手に必要な契約が本計画で確定している。一次資料・依存ライセンス・
  対象規格パラメータ等の技術調査を本 Phase で実施し、未完了ならその旨を明記する。
- **依存**: なし（起点）。

### Phase 1: crate 骨格・CLI / API 契約・モック
- **作業**: Cargo プロジェクト作成、`clap` による `list-devices` / `server` 実装、`/version` と
  `/stream` のスタブ（テスト限定のモック TS を chunked 配信）、エラー型と設定構造体の定義。
- **成果物**: ビルド可能な crate、テスト限定のモックで chunked 配信する HTTP API、CLI 契約。
- **完了条件**: `cargo fmt && cargo check && cargo test && cargo clippy` が通り、
  `/stream?ch=19` がテスト限定のダミー TS を chunked で返し、`/version` が JSON を返す。
  モックはテスト / 開発時のみ有効とし、本番経路で無信号時にダミー TS を返さないことを保証する。
- **依存**: Phase 0。

### Phase 2: N100 実機受信 / IQ
- **作業**: `librtlsdr` 経由のデバイス列挙・受信、IQ のファイル / バッファ入力（テスト用 replay）、
  リサンプルまでのフロントエンド。N100 実機で受信レートと USB 安定性（取りこぼし・切断・再オープン）
  を確認する。N100 検証開始時に device 種別・実受信可能 ch・環境を記録する。IQ fixture は
  自作録画可能とし、配布権利を確認する。録画の提供は必須にしない。周波数対応表を検証する。
- **成果物**: 受信層、IQ replay 入力、フロントエンド DSP、受信レート / USB 安定性の記録、
  検証済み周波数対応表。
- **完了条件**: `list-devices` が実デバイスを列挙し、IQ replay で後段へサンプルを供給できる。
  N100 で目標レートの IQ を継続受信でき、対応表の中心周波数・セグメント位置が一次資料と一致する。
- **依存**: Phase 1。

### Phase 3: scalar 基準 DSP / FEC TS PoC
- **作業**: scalar 基準で各段を段階的に実装・検証する。FFT など成熟した実用ライブラリで
  代替できる部分は再実装しない。scalar 基準は必要な箇所に限定する。
- **中間到達点**:
  - **3a 同期・TMCC**: Mode / GI を同期で推定し、TMCC から階層の変調 / 符号化 / TI を取得できる。
  - **3b 復調・FEC**: キャリア抽出 / 等化から RS(204,188) までの復調・FEC を通過できる。
  - **3c TS 出力と性能測定**: 188 byte TS を出力し、実時間性を初期測定する。
- **成果物**: scalar 参照実装、既知ベクトルによる復調 / FEC / TS / CRC 一致テスト、TS 出力、性能初期値。
- **完了条件**: 既知ベクトル / 合法な録画 IQ から正しい TS（CRC・continuity 含む）を再現できる。
  N100 で未測定なら未達と明記する。
- **依存**: Phase 2。

### Phase 4: 単一 HTTP 統合
- **作業**: §7 の状態機械（`reacquiring` を含む）、追加 `GET /stream` の単一流枠排他
  （同一 ch・別 ch とも 409）、tuning 段階からの原子的予約、単一有界 queue での `/stream` 実配信、
  `/version` の全状態通常応答（§4）、リソース解放。
- **成果物**: 実デバイスからの chunked TS 配信、排他・切断・エラー応答、リソース解放。
- **完了条件**: 追加 `GET /stream` の並行要求 409、同一 ch 拒否、tuning 中予約、
  `reacquiring` 中の 409、disconnect 後に cleanup / cancel / join 完了を経た予約解放、
  `/version` が全状態で通常 200 JSON を返し受信状態を変えないこと、遅読終了、
  無信号時の挙動が仕様どおり。
- **依存**: Phase 3。

### Phase 5: N100 SIMD（AVX2 等）と長時間受入
- **作業**: Phase 3 の計測でホットスポットを特定し、実用 SIMD を優先して N100 に AVX2 等を適用。
  自前 intrinsics は必要箇所のみ。scalar fallback と feature dispatch を用意する。
- **成果物**: N100 向け ISA 別最適化、scalar / SIMD 一致テスト、N100 実時間計測。
- **完了条件**: N100 で実時間処理を実測する。**30 分連続を技術側の初期検証基準**として選定する。
  これは技術側の初期検証基準であり、ユーザー承認済みとも追加承認不要とも記載しない。
  CPU / RSS / 遅延を測定した後に性能予算を確定する。未測定のまま達成と記載しない。
- **依存**: Phase 4。

- **完了条件**: N100 と OrangePi PC2 の両実機で実時間処理を実測する。arm 設計と scalar fallback は

- **成果物**: 配布物とユーザー / 運用文書、既知制約の明記。
- **完了条件**: 目標時間の連続処理で USB 取りこぼし・メモリ増加・ハンドル漏れがない。

## 10. 検証戦略 / テスト計画

### 10.1 テスト計画
- **DSP / FEC 単体**: 合成信号・既知ベクトルによる各段（同期・等化・Viterbi・RS 等）の
  入出力一致。FFT は成熟した実用ライブラリを利用し、再実装しない。TS パケット、CRC、
  continuity counter の検証。
- **IQ replay**: 録画 IQ の期待値との一致、および再生可否。fixture は自作録画可、
  配布権利は Phase 0 で確認する。
- **統合 / 排他**:
  - 追加 `GET /stream` への並行要求が 409 になること（`tuning` / `reacquiring` /
    `stopping` 中の追加要求を含む）。
  - 同一 ch の追加 `GET /stream` も拒否されること。
  - `/version` が `tuning` / `locking` / `streaming` / `reacquiring` / `stopping` /
    `error` の全状態で `200` JSON を返すこと。
  - `/version` の同時取得でも `200` JSON が返り、受信状態と受信枠が変化しないこと。
  - デバイス未接続（device unavailable）でも `/version` が応答すること。
  - `/version` が長い DSP 処理を待たずに応答すること。
  - tuning 中に予約が成立すること。
  - `reacquiring` 中も追加 `GET /stream` が 409 になること。
  - 再取得失敗で `stopping` へ遷移し、サーバが当該接続を終了すること。
  - disconnect 後に cleanup / cancel / join 完了を経て予約が解放されること。
  - 予約解放後は次の要求が成功すること。
  - TS を PID 選別・再多重化しないこと（受信ワンセグ分をそのまま出力）。
  - 多重配信 / fanout を提供しないこと（追加 `GET /stream` を排他する）。
  - signal 失敗 / USB 抜去時の挙動。
  - 有界 buffer の溢れで当該接続のみ終了すること。
  - IQ queue 満杯時の drop を検出して再同期し、無言で隠さないこと。
- **ISA 間**: scalar と SIMD の結果一致、許容誤差の妥当性を両アーキテクチャで比較。
- **品質ゲート**: `cargo fmt` / `cargo check` / `cargo test` / `cargo clippy`。
  aarch64 の cross build は**実行時検証の代替にならない**（実機実行で確認する）。
- **方針テスト**: 監視対象に Python 依存が無いこと（no-python）。N100 先行 → ARM 後続の順序。
- **現状**: 本リポジトリにはまだアプリケーションが存在しないため、上記テストは
  「実施済み」ではなく「これから実施する計画」である。

### 10.2 リスク
- **規格の複雑さ**: ISDB-T 復調・FEC の実装量が大きく、仕様解釈の誤りが手戻りになる。
- **実時間性**: ワンセグでも CPU・USB 帯域・負荷が問題になり得る。早い段階の PoC 測定で検知する。
- **実機・実 IQ の入手**: N100 への RTL-SDR 引渡しと OrangePi PC2 の準備が整わないと Phase 6 が進まない。
- **ライセンス・権利**: 自プロジェクトライセンスは希望なし。既存復調コードの再利用は候補ごとに
  事前確認が必要で、確認漏れ・無断コピーは手戻り（§3・§4）。
- **性能報告の信頼性**: 未測定を達成と扱うリスク。計測値と条件を必須記録とする。
